# 第5段階 実施報告

第5段階のうち、1〜4（点検・自動テスト・修正）を実施しました。5（実機での確認）と 6（公開手順書）は未実施です。

## 1. 権限の総点検

| 確認 | 結果 |
| --- | --- |
| ログインが必要な全36画面に、役割の確認があるか | ✅ すべてあり（パスワード設定画面は修正後）。役割は URL ごとの決まり（proxy と同じ）と一致 |
| サーバーの処理（Server Actions）40個に、役割の確認があるか | ✅ ログイン前に使う5個（ログイン・新規登録など）を除く35個すべてにあり |
| 上の2つを自動テスト化 | ✅ `tests/unit/guards.test.ts`。今後、確認を忘れた画面・処理を追加するとテストが失敗する |
| 画面から送られる値を、サーバーで確かめているか | ⚠️ 来店の「完了／再開」の値を確かめていなかった → 修正 |
| パスワード設定画面 | ⚠️ 画面側でログインを確かめていなかった（処理側では確認済みのため実害なし）→ 修正 |

## 2. 安全性の点検

| 確認 | 結果 |
| --- | --- |
| 本番で使う部品の既知の脆弱性（`npm audit --omit=dev`） | ✅ 0件 |
| 開発用の部品の既知の脆弱性 | ⚠️ 5件（high）。ESLint 内部の `braces` に由来し、信頼できない入力を扱わないため影響なし。アプリには含まれない |
| 秘密のキー（service_role）の使用箇所 | ✅ `src/lib/supabase/admin.ts` だけ（サーバー専用） |
| 画面側のコードから、サーバー専用の値・処理を読んでいないか | ✅ なし |
| HTML の直接埋め込み（XSS の原因） | ✅ なし |
| 本番のセキュリティヘッダー | ✅ CSP（nonce）、HSTS、フレーム禁止、MIME 推測禁止、リファラー制限、カメラ以外の権限を禁止。ログインが必要な画面はキャッシュしない |
| ログインしていない人が、Supabase の API を直接使った場合 | ✅ 全20テーブル・全関数・写真の保存場所が「権限なし」（手元の Supabase で実際に確認） |
| メールのリンクから戻るときの移動先 | ⚠️ 検索条件付きの移動先が正しく扱われなかった → 修正。外部サイトへの移動は従来どおり不可 |

## 3. 画面の自動テスト（E2E）

手元で本物と同じ Supabase（Docker）を起動し、本番ビルドのアプリをスマホの画面サイズで操作するテストを追加しました（`npm run test:e2e`）。

| テスト | 結果 |
| --- | --- |
| ログインしていなければ、業務画面はログイン画面へ移動する | ✅ |
| ログイン後の移動先に外部のサイトは指定できない | ✅ |
| 一般ユーザーはサロン・管理の画面を開けない | ✅ |
| スタッフは管理の画面・セルフ撮影の画面を開けない | ✅ |
| スタッフは担当でない顧客・来店を見られない（管理者は見られる） | ✅ |
| 管理者：効果を約束する説明は保存できず、通常のメニューは登録できる | ✅ |
| スタッフ：顧客登録 → 同意 → 来店 → 問診（通院中）→ 撮影 → 分析 → カウンセリング → 施術案内の承認 → 施術 → 次回メモ → 完了 → 印刷 → 実測値 → 管理者の利用状況 | ✅ |
| 一般ユーザー：同意 → 撮影 → 分析 → セルフケア → 退会 → 退会後はログインできない | ✅ |

あわせて、次のことも確認できました。

- 5つのマイグレーションが、Supabase の実際のデータベース（PostgreSQL 17）でエラーなく適用できること
- **退会の処理が、実際の Supabase の仕組みで動くこと**（第4段階で「未確認」としていた点）
- 写真のアップロードと、スタッフのメモが印刷用の画面に出ないこと

## 4. 見つかった問題と修正

| 問題 | 修正 |
| --- | --- |
| サロンの同意画面で、本人確認のチェックを忘れてエラーになると、入れたチェックがすべて消える | 入れたチェックを残すようにした（自動テストで確認） |
