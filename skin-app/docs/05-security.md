# 05. セキュリティ・個人情報保護設計

> ステータス：**第1段階（設計）— レビュー待ち**
> 法律上の判断（個人情報保護法など）を含む文書（利用規約・プライバシーポリシー・同意文）は、公開前に専門家の確認が必要です。本書は技術的な設計を示すもので、法的な助言ではありません。

## 1. 守るものと想定する脅威

| 守るもの | 主な脅威 | 主な対策 |
| --- | --- | --- |
| 顔写真 | 他人による閲覧、URL の流出、端末への残留 | 非公開の保存場所＋RLS、短い署名付き URL、写真をキャッシュしない |
| 分析結果・カウンセリング内容 | 権限のないスタッフ・他の利用者による閲覧 | 担当割当に基づく RLS、サーバー側での二重確認 |
| 顧客の連絡先 | 情報漏えい | 担当者のみ閲覧、必要最小限の項目 |
| API キー・管理用キー | 端末への露出、リポジトリへの混入 | サーバーの環境変数のみ、`server-only`、秘密情報の検査 |
| 役割（権限） | 自分で管理者になりすます | 役割の列は本人が更新不可、変更は管理者用関数のみ、監査ログ |
| AI の出力 | 診断と誤解される表現、効果の断定 | 指示文での禁止、出力の検査、注意書き、スタッフの承認 |

## 2. 同意の取得

### 2.1 同意の種類（それぞれ別に取得・撤回できる）

| 種類 | 内容 | 同意がない場合 |
| --- | --- | --- |
| 撮影（`photo_capture`） | 肌の見た目を評価する目的で顔を撮影すること | 撮影できない |
| 写真の保存（`photo_storage`） | 写真を保存し、履歴・前後比較に使うこと。保存期間と削除方法 | 撮影・分析はできるが、写真は分析後に削除し、結果の数値・文章だけ残す（第3段階で実装） |
| AI への送信（`ai_processing`） | 縮小した顔画像を外部の AI サービス（Anthropic 社の Claude API）に送り、見た目の説明文を作ること | AI の説明文は作らず、品質チェックと特徴抽出の結果のみ表示 |

### 2.2 AI に送る前の説明（毎回の確認画面 U-05）

同意済みでも、画像を送る直前に次を表示し、「送信して分析する」を押したときだけ送る。

- 送信先：Anthropic 社（Claude API）、送信先の国・地域
- 送るもの：顔写真（縮小済み・位置情報なし）。氏名・連絡先は送らない
- 目的：画像上の見た目の特徴を文章で説明するため
- 送信先でのデータの扱い：送信先の事業者の利用規約・データ保持方針の要点（導入時点の公式の内容を確認して記載し、リンクを付ける）
- 送らない選択もできること

### 2.3 同意の記録

- 誰が・いつ・どの版の文面に・どの方法で（本人のアプリ／サロンのタブレット）同意したかを `consents` に記録する。
- 文面を変更したら新しい版として保存し、次回利用時に再同意を求める。
- 撤回はいつでもできる。撤回後は新しい撮影・保存・送信を止める。保存済み写真の削除方法も案内する。

## 3. 認証

| 項目 | 方針 |
| --- | --- |
| 方式 | Supabase Auth のメールアドレス＋パスワード。メールアドレスの確認を必須 |
| パスワード | 10文字以上。漏えい済みパスワードの検査を有効化（Supabase の設定で可能な場合） |
| スタッフ・管理者 | 管理者の招待メールで作成。**二要素認証（TOTP）を必須**にする（第2段階で仕組み、第5段階で必須化の確認） |
| セッション | Cookie（`HttpOnly`、`Secure`、`SameSite=Lax`）。`middleware.ts` で更新 |
| ログイン試行 | Supabase の制限機能を使う。ログイン失敗の表示は「メールアドレスまたはパスワードが違います」に統一（登録の有無を推測させない） |
| 重要な操作 | 退会・全データ削除・役割変更の前にパスワードの再入力 |

## 4. 認可（アクセス制御）

3段階で確認する。どれか1つが漏れても他で防げるようにする。

1. **画面の振り分け**（`middleware.ts`）：役割に合わない URL は `/403` へ。これは使いやすさのためで、安全の根拠にはしない。
2. **サーバー処理での確認**：Route Handler・Server Action の最初で、ログイン・役割・対象へのアクセス権・同意を確認する共通関数を必ず通す。
3. **データベースの RLS**：最終的な防御。設計は [04-database.md §4](04-database.md#4-rls行レベルセキュリティ方針)。

URL に含まれる ID を書き換えても、他人のデータは RLS で返らない（存在するかどうかも分からないように「見つかりません」と表示）。

## 5. 通信・保存データの保護

| 項目 | 方針 |
| --- | --- |
| 通信 | すべて HTTPS。`Strict-Transport-Security` ヘッダーを設定 |
| 保存データ | Supabase の保存データ暗号化（標準機能）。写真は非公開の保存場所 |
| 写真の URL | 署名付き URL を60秒程度で失効させる。画面以外（メールなど）に URL を載せない |
| EXIF | 端末で写真を描き直して位置情報などを除去してからアップロード |
| 端末への残留 | Service Worker は静的ファイルだけをキャッシュ。写真・API の応答には `Cache-Control: no-store`。ブラウザの保存領域に写真や個人情報を保存しない |
| ログ | サーバーのログに写真・氏名・連絡先・AI の応答本文を出さない（ID のみ） |

### 5.1 HTTP セキュリティヘッダー

- `Content-Security-Policy`：自分のドメインと Supabase のみ許可。インラインスクリプトは nonce 方式。`frame-ancestors 'none'`
- `X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(self), geolocation=(), microphone=()`

## 6. 秘密情報の管理

- `ANTHROPIC_API_KEY`、`SUPABASE_SERVICE_ROLE_KEY` は**サーバーの環境変数のみ**。`NEXT_PUBLIC_` を付けない。
- これらを使うファイルの先頭に `import 'server-only'` を書き、端末側のコードに混ざると組み立て時にエラーになるようにする。
- `.env*` は `.gitignore` 済み。`.env.example` には値を書かない。
- 組み立て後の端末向けファイルに秘密情報が含まれていないかを、テストで文字列検索する（第5段階）。

## 7. AI出力の安全対策

| 対策 | 内容 |
| --- | --- |
| 指示文での制限 | 見た目の特徴の説明に限定。病名・診断・治療・肌年齢・水分量や油分量などの数値・効果の保証を書かないよう指示 |
| 出力形式の固定 | 構造化出力（JSON スキーマ）で受け取り、Zod で検証。形が違えば使わない |
| 禁止表現の検査 | 病名・医療用語・薬機法などで問題になりやすい断定表現（「治る」「改善する」「〜に効く」「必ず」など）の一覧で検査し、該当する文は表示しない。除いた件数を記録 |
| 固定の注意書き | AI の出力とは別に、アプリ側で注意書きと医療機関への相談の案内を必ず表示（AI の出力に頼らない） |
| 根拠の制限（施術案内） | 管理者が登録したメニューの情報だけを渡す。スタッフの承認後に顧客へ表示 |
| モック表示 | 検証されていない評価には「モック（未検証）」を表示し、精度があるように見せない |

禁止表現の一覧は管理画面から更新できるようにする（第4段階）。

## 8. 入力検証・一般的な脆弱性対策

| 脆弱性 | 対策 |
| --- | --- |
| 不正な入力 | 画面とサーバーの両方で同じ Zod スキーマで検証。文字数の上限を設定 |
| SQL インジェクション | Supabase のクライアント（パラメーター化）だけを使い、SQL を文字列でつなげない |
| XSS | React の自動エスケープ。`dangerouslySetInnerHTML` を使わない。AI の出力も文字列として表示 |
| CSRF | Server Action の標準の保護＋ `SameSite` Cookie。Route Handler は `Origin` ヘッダーを確認 |
| ファイルアップロード | JPEG のみ、サイズ上限、保存先は RLS で制限。サーバー側でも画像として読めるか確認してから AI に送る |
| 使いすぎ・攻撃 | AI の利用回数の上限、ログイン試行の制限 |
| 依存ライブラリ | `npm audit` と Dependabot で確認（第5段階） |

## 9. 監査ログ

記録する操作（`audit_logs`）：

- ログイン関連は Supabase Auth の記録を使う
- 写真：アップロード、表示（署名付き URL の発行）、削除
- 分析：実行、AI への送信、削除
- 顧客：作成、更新、削除。担当の割当・解除
- 同意：取得、撤回
- 管理：役割の変更、スタッフの招待・停止、メニュー・料金の変更、設定の変更
- 退会・全データ削除

監査ログは追記のみ（更新・削除の権限を誰にも与えない）。記録する関数は操作した人を `auth.uid()` から自動で設定し、なりすましを防ぐ。個人情報（氏名・写真）は記録しない。

## 10. 退会・データ削除の手順

1. 本人が設定画面で「退会する」を選ぶ
2. 削除されるもの（写真・分析・記録・同意の記録の扱い）と、元に戻せないことを表示
3. パスワードを再入力
4. サーバー：Storage の本人の写真をすべて削除 → データベースの本人のデータを削除 → 認証のアカウントを削除
5. 監査ログに「退会処理を行った」ことと件数だけを記録
6. 完了画面とログアウト

途中で失敗した場合は、管理者画面に「削除が完了していないアカウント」として表示し、再実行できるようにする。

## 11. 第5段階で行う確認

- 役割ごとのアクセス確認表（3つの役割 × 全テーブル × 読む／作る／変える／消す）を自動テストで確認
- 他人の ID を指定したアクセスが拒否されることのテスト
- 停止したスタッフ・担当を外されたスタッフがアクセスできないことのテスト
- 端末向けファイルに秘密情報が含まれていないことの確認
- HTTP ヘッダーの確認、依存ライブラリの脆弱性確認
- Supabase のセキュリティ診断機能（Security Advisor）での確認
