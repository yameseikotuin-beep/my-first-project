# 01. 要件定義

> ステータス：**承認済み**（2026-10-03）。実装との差分は [stage2-report.md §5](stage2-report.md#5-設計からの変更点) を参照。
> 「要確認事項」（§6）は、仮の前提のまま承認されました。

## 1. 目的とスコープ

1つのアプリ（Webアプリ / PWA）で、次の3つの利用形態をまとめて扱う。

| 利用形態 | 主な利用者 | 主な端末 |
| --- | --- | --- |
| セルフ肌分析・記録 | 一般ユーザー | スマートフォン |
| 肌分析・美容カウンセリング | サロンスタッフ | タブレット / PC（撮影はスマホ・タブレット） |
| 顧客・施術・スタッフの管理 | 管理者 | PC |

### 1.1 本アプリが「やること」

- 顔写真の、**画像上の見た目の特徴**の評価・説明・記録
- 撮影条件（明るさ・角度・距離・ブレ）の確認と記録
- 美容カウンセリングの補助（問診・カウンセリングシート・施術履歴・前後比較）
- 管理者が登録した施術メニューの情報をもとにした、**一般的な案内文**の作成補助

### 1.2 本アプリが「やらないこと」（医学的な制約）

| 禁止事項 | 実装での担保 |
| --- | --- |
| 皮膚疾患の診断・病名の提示 | AIへの指示で禁止し、出力を検査して病名・医療用語を含む文を除く（[05-security.md §7](05-security.md#7-ai出力の安全対策)） |
| 治療方針の判断 | 同上。施術案内は「一般的な美容ケアの紹介」の表現に限定 |
| 肌年齢、水分量・油分量などの数値を写真から出すこと | 該当する評価項目を作らない（データベースに列が存在しない） |
| 施術効果の保証 | 案内文に効果の断定表現を使わない。スタッフの確認・承認がないと顧客に表示しない |
| AIの評価と測定機器の実測値の混同 | 別テーブルで保存し、画面上で「AIによる推定」「機器による実測」とラベルを分ける |

すべての分析結果には次を常に表示する。

- 撮影条件と撮影品質
- 「AIによる画像上の推定であり、診断ではありません」という注意書き
- 確信度（項目ごと）
- 赤みや色ムラが強いなど、異常が疑われる場合の **医療機関への相談案内**
- 検証済みでない評価機能を使った場合の **「モック（未検証）」** 表示

## 2. 利用者と権限

| 役割 | 内部名 | 作り方 |
| --- | --- | --- |
| 一般ユーザー | `user` | 本人がメール登録（新規登録の既定値） |
| サロンスタッフ | `staff` | 管理者が招待メールで作成。本人は自分の役割を変えられない |
| 管理者 | `admin` | 初期の管理者は導入時にコマンドで作成。以降は管理者が任命 |

### 2.1 権限マトリクス

○＝可能、△＝条件付き、×＝不可

| 操作 | 一般ユーザー | スタッフ | 管理者 |
| --- | --- | --- | --- |
| 自分の写真撮影・肌分析・履歴閲覧 | ○ | ○※1 | ○※1 |
| 自分のセルフケア記録・経過グラフ | ○ | ○※1 | ○※1 |
| 自分の写真・分析の削除、退会 | ○ | ×※2 | ×※2 |
| 顧客の新規登録 | × | ○（登録者は自動で担当に） | ○ |
| 顧客情報・写真・分析の閲覧／編集 | × | △ 担当として割り当てられた顧客だけ | ○ 全顧客 |
| 問診・カウンセリング・施術記録の作成 | × | △ 担当顧客だけ | ○ |
| 施術案内文の生成・承認 | × | △ 担当顧客だけ | ○ |
| 顧客の削除 | × | × | ○ |
| メニュー・料金・説明文の編集 | × | 閲覧のみ | ○ |
| スタッフの招待・役割変更・担当割当 | × | × | ○ |
| 分析件数・利用状況・監査ログの閲覧 | × | × | ○ |

- ※1 スタッフ・管理者も個人としてセルフ分析を使える設計にするかは要確認（初期案：使えない。業務アカウントと個人アカウントを分ける）。
- ※2 スタッフ・管理者アカウントの削除は管理者が行う。

**一般ユーザーは、他人の情報に一切アクセスできない。** 画面上で隠すだけでなく、データベースの行レベルセキュリティ（RLS）で拒否する（[04-database.md §4](04-database.md#4-rls行レベルセキュリティ方針)）。

## 3. 機能要件

段階の列は、その機能を実装する予定の開発段階。

### A. 顔写真撮影（第2段階）

| ID | 要件 |
| --- | --- |
| A-1 | スマートフォン・タブレットのカメラで撮影（ブラウザの `getUserMedia`、インカメラが既定） |
| A-2 | 写真ファイルのアップロード（JPEG / PNG / HEIC。HEIC はブラウザが読めない場合は案内を出す） |
| A-3 | 正面 → 左 → 右 の順の撮影ガイド。顔の位置を示す枠を画面に重ねて表示 |
| A-4 | 撮影前・撮影後の品質チェック：明るさ、ブレ、顔の向き（左右・上下の角度）、距離（画面内の顔の大きさ）。基準外なら理由を示して撮り直しを案内 |
| A-5 | 撮影条件の記録：撮影日時、角度、品質チェックの値、撮影した人（本人 / スタッフ）、端末の種類（スマホ / PC 程度。機種名や位置情報は保存しない） |
| A-6 | 写真の位置情報などのメタデータ（EXIF）は端末内で取り除いてからアップロード |
| A-7 | 顔の検出は端末内で行い、この段階では外部サービスに画像を送らない |

### B. 肌画像分析（第3段階）

| ID | 要件 |
| --- | --- |
| B-1 | 評価項目：毛穴の目立ち／赤み／色素斑のように見える部分／キメ・質感／肌表面の特徴（くすみ・てかりの見え方など） |
| B-2 | 部位：額、左右の頬、鼻、あご、目の下 |
| B-3 | 項目×部位ごとに、5段階の見え方の評価、確信度、判定できたかどうか、説明文 |
| B-4 | 撮影品質が基準未満、または確信度が低い項目が多い場合は、結果を出さずに**再撮影を案内**する |
| B-5 | 特徴抽出は差し替え可能な独立モジュールにする（[03-architecture.md §4](03-architecture.md#4-画像解析モジュール設計)）。第3段階ではモック実装のみで、画面に「モック（未検証）」と常に表示 |
| B-6 | Claude API は**見た目の特徴の文章による説明**に使う。採点（数値）は Claude にさせない |
| B-7 | 画像をAIサービスに送る前に、送信先・目的・保存の有無を説明する確認画面を出し、同意がない場合は送らない |

### C. 分析レポート（第3〜4段階）

| ID | 要件 |
| --- | --- |
| C-1 | 顔の図に部位ごとの評価を重ねて表示 |
| C-2 | 見た目の特徴の説明、注意事項、セルフケアの一般情報 |
| C-3 | 過去の結果との比較（同じ項目・部位の推移。撮影条件が大きく違う場合は「比較の精度が低い」と表示） |
| C-4 | 印刷用レイアウト（ブラウザの印刷機能から PDF 保存）。注意書き・撮影条件・モック表示を必ず含める |

### D. 一般ユーザー機能（第4段階）

| ID | 要件 |
| --- | --- |
| D-1 | 自分の分析履歴と写真の一覧 |
| D-2 | セルフケア記録（日付、行ったケア、使ったもの、メモ、睡眠などの任意項目） |
| D-3 | 項目ごとの経過グラフ |
| D-4 | 写真1枚ずつの削除、分析1件ごとの削除、全データ削除、退会 |
| D-5 | 同意の確認と撤回（撤回すると以後のAI送信・写真保存を止める） |

### E. サロン機能（第2段階：台帳 / 第4段階：その他）

| ID | 要件 |
| --- | --- |
| E-1 | 顧客台帳：氏名、ふりがな、連絡先、生まれ年（任意）、メモ、担当スタッフ。検索・並び替え |
| E-2 | 来店記録：来店日、担当、行ったこと |
| E-3 | 問診：肌の悩み、アレルギー・敏感肌の有無、通院中の皮膚の病気の有無（ありの場合は施術前に医師への確認を促す表示）、当日の体調 |
| E-4 | サロンでの撮影と肌分析（A・B と同じ機能を、顧客を対象に実行） |
| E-5 | カウンセリングシート：悩み、分析結果の要点、提案内容、顧客の希望、スタッフのメモ |
| E-6 | 施術メニューの選択と施術履歴（その時点の料金を記録） |
| E-7 | 次回来店メモ |
| E-8 | 施術前後の写真比較（並べて表示・スライダーで重ねて表示）。撮影条件の違いも並べて表示 |
| E-9 | サロンで顧客の同意を取る画面（タブレットで顧客本人が読んで同意。誰が・いつ・どの版の同意文で取ったかを記録） |
| E-10 | 測定機器の実測値の手入力（機器名・項目・値・単位）。AIの評価とは別枠で表示 |

### F. 施術案内（第4段階）

| ID | 要件 |
| --- | --- |
| F-1 | 管理者が登録したメニュー情報（名前・説明文・注意事項・料金）だけを根拠に、関連するケアの案内文を Claude で下書きする |
| F-2 | 登録されていない施術や効果を書かない。効果の保証、医療行為と誤解される表現を禁止 |
| F-3 | 下書きはスタッフが編集・承認してから顧客に見せる（承認者と日時を記録） |
| F-4 | 美容鍼などメニューに資格・禁忌の注意事項がある場合は、その注意事項を必ず案内文に含める |

### G. 管理者機能（第2段階：権限 / 第4段階：その他）

| ID | 要件 |
| --- | --- |
| G-1 | スタッフの招待・停止・役割変更、顧客の担当割当 |
| G-2 | 全顧客の管理、顧客の削除 |
| G-3 | メニュー・料金・説明文・注意事項の編集、公開／非公開 |
| G-4 | 分析件数（日別・スタッフ別・セルフ/サロン別）、AI 利用回数 |
| G-5 | 監査ログの閲覧・絞り込み |
| G-6 | 同意文・注意書きの版管理（文面を変えたら新しい版として保存し、既存の同意は旧版のまま記録に残す） |

## 4. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 対応端末 | iOS Safari / Android Chrome の最新2版、PC の Chrome / Edge / Safari 最新版 |
| 画面 | スマホは片手操作（主ボタンは画面下部）、PC は一覧と詳細を並べるダッシュボード |
| 文字 | 本文 16px 以上、行間 1.7 程度、色のコントラスト比 4.5:1 以上（WCAG 2.2 AA を目標） |
| 操作性 | キーボード操作、スクリーンリーダー用のラベル、動きを減らす設定への対応 |
| 性能 | 画面表示 2.5 秒以内（4G 回線想定）。AI 分析は 30 秒程度を想定し、進み具合を表示 |
| PWA | ホーム画面に追加できる。オフライン時は静的な画面だけ表示し、**個人情報や写真は端末にキャッシュしない** |
| 言語 | 日本語（文言は1か所にまとめ、将来の多言語化に備える） |
| 可用性 | Supabase・ホスティングの標準構成に従う（専用の冗長化はしない） |

## 5. 開発段階と、各段階の完了条件

| 段階 | 内容 | 完了条件 |
| --- | --- | --- |
| 1 | 要件・画面・構成・DB・セキュリティ設計（本書） | 設計の承認と要確認事項への回答 |
| 2 | 認証、役割と権限、基本画面、顧客台帳、撮影・アップロード | 3つの役割でログインでき、RLS のテストが通り、撮影した写真が本人／担当者だけに見える |
| 3 | 画像解析の仕組み（モック）、Claude 連携、分析レポート | モック表示つきで分析レポートが出る。API キー未設定時は「AI未接続」と表示して動く |
| 4 | セルフ管理、カウンセリング、施術履歴、前後比較、PDF、案内文 | 各機能の画面とテスト |
| 5 | テスト、脆弱性確認、権限確認、実機確認、導入手順書 | 確認結果の報告書と手順書 |

各段階の終わりに、**完成した機能／モックの機能／外部 API 未接続の箇所／未実装の機能** を一覧で報告する。

## 6. 要確認事項

以下は仮の前提で設計しています。違う場合は教えてください。

| # | 確認したいこと | 仮の前提 |
| --- | --- | --- |
| Q1 | サロンは1店舗ですか、複数店舗・複数企業ですか | **1つの導入につき1サロン（複数スタッフ）**。複数店舗は将来対応 |
| Q2 | 一般ユーザーとサロンの顧客は、同じ人でもデータをつなげますか | **つなげない**（セルフのデータとサロンのデータは別管理） |
| Q3 | 写真の保存期間 | セルフ：本人が削除するまで。サロン：最終来店から3年で自動削除の候補を管理者に通知 |
| Q4 | 未成年の利用 | **18歳未満は利用不可**（登録時に確認） |
| Q5 | 予約や支払いの機能は必要ですか | **不要**（料金は表示・記録のみ） |
| Q6 | スタッフ・管理者が個人としてセルフ分析を使えるようにしますか | 使えない（個人用は別アカウント） |
| Q7 | ホスティング先 | Vercel ＋ Supabase（東京リージョン） |
| Q8 | 利用規約・プライバシーポリシーの文面 | 雛形を用意するが、**公開前に専門家（弁護士等）の確認が必要** |
